# N4 Monitor 接入 Agent 方案简报

调研日期：2026-10-22。基于本地源码 `c2b33ff`、论文和框架官方资料；本次完成方案调研，尚未进行接入实验。

## 1. 结论

**可以接入，优先选择“自然语言配置告警规则＋回放反馈纠错”，再扩展告警证据分析。** 这条路线能同时形成工程功能与定量实验，且不依赖真实设备故障标签。

建议题目：**《基于工具增强智能体的设备告警规则辅助配置与分析系统设计与实现》**。

低算力路线是：大模型使用云端 API，检索、统计、规则校验和回放在本机 CPU 执行，无需训练或微调大模型。云端调用仍有费用和网络依赖；离线评测可使用固定数据快照与内存回放，减少运行整套中间件的资源开销。

## 2. 工程侧：可以做哪些功能

| 方案 | 用户看到的功能 | 主要新增工作 | 适合程度 |
|---|---|---|---|
| **规则配置 Agent** | 输入“达到 30°C 持续 120 秒报警，低于 28°C 恢复”，得到可审核规则 | 点位定位、结构化草稿、参数校验、隔离回放、根据错误修正、审核与版本记录 | **首选：业务边界清楚，效果容易核验** |
| **告警分析 Agent** | 点击告警，解释触发条件、等级变化和建议补查内容 | 查询实时值、历史窗口、当时规则与资料；按需补查；输出带证据的分析 | 推荐扩展；证据不足时只能给排查方向 |
| 设备资料问答 | 查询设备手册、操作步骤和相似案例，并跳转原文 | 资料导入、设备关联、检索、引用核验 | 容易起步，但依赖资料质量，单独做工作量偏薄 |
| 巡检／交接简报 | 汇总指定时段异常、未确认告警和处理建议 | 时段统计工具、异常筛选、补查、来源追溯和简报记录 | 展示直观，适合附加功能 |

Agent 的关键是**调用工具、观察结果，再决定补查或修正**。只有聊天框、固定模板摘要或一次 RAG 问答，难以体现完整 Agent 工作量。可借鉴 [ReAct 的推理与工具交互模式](https://arxiv.org/abs/2210.03629)。

当前项目已有规则 CRUD、Redis 同步、告警状态机、历史事件与 Vue 页面，可作为底座。需要先补的内容主要有：

- **回放服务**：`AlarmHarness` 已能用内存 Redis 和可控定时器驱动生产告警逻辑，但仍是测试夹具，需封装为隔离回放工具。
- **可靠证据查询**：部分点位和 Dashboard 数据由随机数生成；分析工具应读取实际数据或明确标记的固定模拟快照，并支持按点位、观测时间查询。历史分析还需要规则版本。
- **工具边界**：沿用后端身份认证，补用户设备范围过滤；规则先生成草稿，由有权限的用户审核后保存，同时处理目标点位绑定并展示共享规则的受影响点位范围。

源码依据：[回放夹具](../monitor-flink-job/src/test/java/com/n4monitor/flink/AlarmHarness.java)、[规则执行逻辑](../monitor-flink-job/src/main/java/com/n4monitor/flink/RuleEvaluator.java)、[告警查询接口](../monitor-backend/src/main/java/com/n4monitor/alarm/controller/AlarmController.java)、[模拟点位接口](../monitor-backend/src/main/java/com/n4monitor/device/controller/MonitorPointController.java)。

## 3. 算法侧：低算力、可做对比实验的方向

| 方向 | 在本项目中怎么做 | 对比与指标 | 判断 |
|---|---|---|---|
| **工具反馈驱动规则纠错** | 生成规则→校验→用真实告警逻辑回放→返回具体错误→限次修正 | 一次生成、仅参数校验、加入回放反馈；比较行为通过率、修正次数和调用成本 | **最推荐**；借鉴 [CRITIC](https://arxiv.org/abs/2305.11738) 与 [Self-Debugging](https://arxiv.org/abs/2304.05128) 的工具／执行反馈思路 |
| **预算约束的证据工具选择** | 根据缺失事实和剩余调用预算，选择查历史、查规则或查资料；满足条件后停止 | 固定全量查询、普通 ReAct、加入预算与证据约束；比较事实正确率、无依据结论比例、调用量 | 适合告警分析；需自行定义证据充分条件 |
| **设备约束检索与案例记忆** | 先按设备类型、点位、规则版本过滤，再做关键词检索；只存审核后的成功案例 | 普通关键词检索、加入元数据过滤、再加入案例记忆；比较 Hit@k、回答正确率 | CPU 可做；资料建设是主要工作，记忆思路可参考 [Reflexion](https://arxiv.org/abs/2303.11366) |
| **轻量异常检测工具** | 从时序窗口提取均值、波动、变化率，采用 MAD 或 Isolation Forest 检测异常，再交给 Agent 解释 | 固定阈值、MAD、Isolation Forest；比较事件级 F1、误报和检测延迟 | 算法备选；小规模 CPU 可运行，树模型仍需拟合，参考 [官方实现](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.IsolationForest.html) |

这些是**候选方法改进与业务实验方向**。调用框架、接入 RAG 或使用现成检测器本身不等于算法创新；需要明确改了什么，并用基线和消融实验验证。异常检测只能证明“发现异常”，不能直接证明“找到物理故障根因”。

## 4. 推荐落地与最小实验

**首版只做规则配置闭环：** 自然语言需求→查点位与引擎能力→规则草稿→参数校验→隔离回放→最多两轮修正→展示差异→人工审核。

先限定为现有引擎支持的单点数值／枚举规则、延迟和死区。严格比较、跨点组合等无法等价表达的需求应澄清或说明能力不足。

回放只产生实际行为；判定行为是否符合意图，还需要用户确认或人工编写的独立预期。实际交互没有预期时，展示轨迹供用户核对，不能由 Agent 自设答案后宣称验证正确。

技术路线有两种：

- **便于算法实验：Python＋LangGraph 独立服务，经 HTTP 调用 Java 工具接口。** 可以组合确定性节点、模型节点和人工审核；首版无需额外引入 gRPC 或多 Agent。[LangGraph 官方文档](https://docs.langchain.com/oss/python/langgraph/overview)
- **便于保持 Java 技术栈：Spring AI 2。** 当前项目为 Spring Boot 4.0.7／Java 21，官方明确 Spring AI 2.0.x 支持 Boot 4.0.x／4.1.x；仍需验证项目依赖集成。[官方兼容说明](https://docs.spring.io/spring-ai/reference/getting-started.html)

最小实验建议：

1. **数据**：先用 20 条需求跑通，再扩到 100—200 条；覆盖越限、短时尖峰、延迟、死区恢复、等级切换、枚举、缺参数与不支持条件。人工审核标准规则和预期事件序列，预期不能由待测 Agent 自己生成。
2. **公平对比**：同一模型比较“一次生成”“仅校验反馈”“校验＋回放反馈”，再加入同调用预算的无反馈多候选基线：用相同开发回放筛选候选，但不向模型反馈结果。修正环只使用开发场景，最终用隐藏场景评分。
3. **指标与消融**：行为通过率为主，核验触发／恢复时刻与等级；同时记录参数正确率、澄清表现、耗时、tokens 和费用。移除回放反馈或具体错误位置，检验各组件贡献；正式测试独立运行多次，报告波动。
4. **复现**：按设备或场景族划分调参集与测试集，避免同一模板换参数后跨集；锁定模型版本、提示词、依赖、场景种子与回放时钟。模拟结果只说明所覆盖场景的效果。

首版工程与实验可按 **4—6 周**安排：约 1 周工具与回放、2 周 Agent 与页面、1—3 周数据和实验；这是熟悉项目的单人全职粗估。

最终可展示的工作量是：**一套可审核的 Agent 业务闭环、一套复用生产逻辑的回放工具、一批可复现测试场景，以及基线／消融／成本实验。** 若时间充裕，再接入告警分析；微调、强化学习训练和多 Agent 辩论不列入首版。
