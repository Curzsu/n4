# N4 Monitor 相近硕士论文调研与选题建议

调研日期：2026 年 9 月 29 日。

调研问题：设备监控、告警分析、大模型辅助运维方向有哪些真实硕士论文，它们怎样组织研究工作、系统实现和实验，哪些做法适合 N4 Monitor。

## 1. 检索范围与证据说明

本次重点检索大学学位论文服务系统、大学机构仓储，以及学校发布的答辩或优秀论文名单。优先选用能够核实作者、学校、年份和硕士论文身份的一手来源。本文是面向选题的定向调研，不是穷尽性的系统文献综述。

使用三种证据层级：

- **正文已核对**：获取公开 PDF，查看封面、目录及与方法、实验有关的关键章节；不表示逐页通读全文。
- **官方摘要已核对**：可以归纳主要研究工作，无法确认原论文逐章目录或未披露的实验细节。
- **官方题录已核对**：学校名单能够确认题目或答辩信息，不能据此推断具体方法和结果。

下文的“可借鉴写法”和 N4 Monitor 章节安排均为本次调研提出的建议。只有明确标为“已核对目录”的内容对应原论文。

### A. 工具增强的大模型根因分析

**核实的研究内容：**论文提出 RCAgent，通过工具 API 收集和分析云平台数据，并研究动作一致性、上下文管理及领域知识增强。摘要说明其在一个月的错误作业上与 ReAct 比较，评估根因、解决方法、证据和故障归属四类输出；应用场景是阿里云实时计算平台的错误诊断。[清华官方摘要](https://newetds.lib.tsinghua.edu.cn/qh/paper/summary?dbCode=ETDQH&sysId=288965)

**可借鉴写法：**把工作组织为“诊断任务定义—数据获取与工具设计—针对任务难点改进框架—分项评估—接入真实系统”。这里归纳的是摘要中的工作逻辑，没有获得硕士论文原始目录。

**对应 N4 Monitor：**将查询设备、活动告警、历史点位、部署变更和依赖关系封装为受权限约束的工具；模型根据已有证据决定补查内容，输出候选原因和引用。软件作业故障与物理设备故障的数据和机理不同，迁移时需要重新设计故障场景和标注。

**建议阅读顺序：**这篇排第一。它与项目已经具备的后端查询能力衔接紧密。另有同名框架的[公开研究论文](https://arxiv.org/abs/2310.16340)可补充方法细节；该研究论文应与硕士论文分开引用。

### B. 故障知识图谱与大模型问答

**核实的研究内容：**摘要将工作分成知识抽取、图谱构建与补全、诊断应用三部分。系统从故障资料提取实体关系，通过图查询召回知识，再由大模型生成回答。官方学科为工程管理；摘要未给出完整实验表和具体提升数值。[清华官方摘要](https://newetds.lib.tsinghua.edu.cn/qh/paper/summary?dbCode=ETDQH&sysId=299990)

**可借鉴写法：**围绕“资料怎样形成知识—知识怎样被检索—检索结果怎样用于辅助诊断”展开，每一步都有可交付的方法或数据成果。

**对应 N4 Monitor：**建设设备型号、故障现象、告警类型、可能原因、排查措施之间的关联，并结合设备手册和确认过的维修案例检索。现有导航树提供组织范围；通信、供电等真实依赖应单独建模并核实。

**课题边界：**可以参考其知识组织思路，是否需要训练实体抽取模型、图谱补全模型，应取决于数据和研究问题。不同学科的硕士要求也需分别考虑。

### C. 自然语言需求与运维求解

**核实的研究内容：**论文构建运维需求数据并进行低秩微调，结合大小模型完成意图解析；对调度和备件问题建立约束模型，使用 OR-Tools 求解，最后实现带权限、数据和决策功能的平台。公开摘要没有完整量化实验细节。[清华官方摘要](https://newetds.lib.tsinghua.edu.cn/qh/paper/summary?dbCode=ETDQH&sysId=302800)

**可借鉴写法：**把语言理解、结构化建模和确定性执行分别说明，并明确它们之间的接口。这种组织方式能够把大模型能力与业务规则结合起来。

**对应 N4 Monitor：**一个范围较清楚的迁移方向是“自然语言告警规则生成与回放验证”：解析点位、单位、阈值和持续时间，生成规则草稿，执行格式及业务校验，用历史数据展示触发效果，再发布版本并记录审计。该迁移方案是本次建议，原论文研究的是调度与库存管理。

### D. 监控界面与大模型辅助诊断的实验

**核实的研究内容：**论文在工业机器人仿真中设置九类故障，并让 22 名参与者经历可视化方式和是否提供大模型辅助的四种组合。评价覆盖诊断正确性、耗时、认知负担和体验。模型输入含故障真值，参与者主要来自高校，其结果应限定为该实验条件下的辅助决策效果。[大学仓储记录](https://reposit.haw-hamburg.de/handle/20.500.12738/19947)

**已核对目录：**第 3 章集中说明系统与模型接入，第 4 章交代实验条件和度量，第 5 章呈现结果，第 6 章解释结果及局限。相关目录在 PDF 第 5—6 页；实验设计从正文第 32 页开始。[公开 PDF](https://reposit.haw-hamburg.de/bitstream/20.500.12738/19947/1/MA_Immersive_data_visualization.pdf)

**对应 N4 Monitor：**可以开展“原告警页面”和“增加证据式诊断建议后的页面”的任务对比，测排查正确性和用时。模型独立定位根因的评估应仅提供当时实际可见的数据；人工确认的根因作为评分依据另行保存。

### E. 从维修记录更新排查知识

**核实的研究内容：**论文以 ASML 维修记录和诊断流程更新为材料，比较四个可本地运行的模型生成排查问题及故障模式。评价同时采用语义相似度和人工两两比较，并指出两者对实用质量的判断并不完全一致。官方页面注明全文尚在禁限期。[TU Delft 官方记录与摘要](https://repository.tudelft.nl/record/uuid:bbcf0a02-a2e6-49d0-9931-935048e86892)

**可借鉴写法：**围绕一个边界清晰的任务，先定义输入输出及数据，再说明评估为何困难，最后用自动指标和人工评价共同分析。

**对应 N4 Monitor：**将已确认故障的“现象—检查过程—实际原因—有效措施”整理成案例，研究模型如何提出知识更新建议，以及如何审核入库。开放式诊断建议的实验应包含相关性、可操作性和证据支撑的人工评价。

### F. 在线监测系统如何形成研究主线

**核实的研究内容：**这篇非大模型论文围绕换流阀及冷却系统，组合物理建模、故障模拟、数据驱动异常感知和诊断，并将方法集成进具有状态展示、告警和辅助处置能力的现场系统。摘要报告了案例验证及持续运行情况。[清华官方摘要](https://newetds.lib.tsinghua.edu.cn/qh/paper/summary?dbCode=ETDQH&sysId=294441)

**可借鉴写法：**选定设备对象和故障类型，解释可观测现象与故障之间的关系，设计方法并验证，然后说明平台如何支撑应用。

**对应 N4 Monitor：**先从一个子系统的通信异常、温度异常等明确场景切入，定义需要哪些点位和状态才能排查。具体故障类型应由现场资料确认。现有平台可以承载数据接入、事件保存和结果展示。

## 4. 对论文写法的归纳

综合上述材料，本次建议采用以下论证顺序：

1. **明确任务与边界**：设备范围、故障类型、输入信息、期望输出、使用者。
2. **指出可验证的困难**：例如资料分散、时间错位、缺少依赖关系、诊断结论无法追溯。
3. **提出具体处理方法**：说明输入怎样处理、怎样检索、怎样调用工具、怎样判断证据是否充分。
4. **实现可运行系统**：解释与监控平台的接口、数据模型、权限、异常处理和页面交互。
5. **用对照实验回答研究问题**：不同方案使用一致的数据划分和明确的评价规则。
6. **分析失效情况和适用条件**：包括真实数据与模拟数据、已知故障与未见故障、信息完整与缺失的区别。

这是面向 N4 Monitor 的综合建议，不是任何一篇论文的原始目录，也不代表所有硕士论文必须采用同一结构。

**《面向设备监控的多源证据增强故障辅助诊断系统设计与实现》**

**《融合设备拓扑与检索增强大模型的故障辅助诊断方法研究与实现》**

这些均为候选题目。研究贡献需要进一步与同类工作比较，并通过实验确认。

### 5.2 现有成果如何纳入

| 现有能力 | 在课题中的用途 | 建议补充的成果 |
|---|---|---|
| 设备模板、部署层级、批量导入及移动 | 设备身份和组织范围 | 设备依赖、路径版本与资料关联 |
| MQTT、Kafka、Flink 告警处理 | 获取实际异常和生命周期 | 故障事件聚合、诊断触发接口 |
| 历史事件和时序数据查询 | 获取故障前后证据 | 时间窗口摘要、关键证据定位 |
| 实时页面、历史页面、设备视图 | 承载运维任务 | 诊断卡片、来源跳转、人工反馈 |
| 权限与审计 | 控制数据访问、记录操作 | 模型工具调用范围和诊断过程留痕 |

以上以此前对项目代码的检查为基础，本次未启动服务或重新验证运行效果。

### 5.3 两个候选研究问题

**问题一：加入设备身份、时间窗口和依赖关系约束，能否提高故障证据检索质量？**

拟研究多源证据的统一表示、时间对齐、检索过滤与排序。证据可以包含活动告警、历史点位摘要、部署变更、手册段落和维修案例。原始数值统计由后端执行，模型消费可追溯的统计结果。

可比较普通文档检索、设备范围约束检索、进一步加入时间与依赖关系的检索。观察相关证据召回、干扰信息比例、诊断效果、上下文长度和调用成本。

**问题二：受控工具查询和证据校验，能否提升诊断建议的可靠性？**

拟实现有界的补充查询流程，输出候选原因、支持证据、尚缺信息和排查建议。程序检查引用、设备标识和数值，人工评估诊断逻辑与措施是否合理。事实字段校验的能力边界与根因判断本身应分别说明。

模型实际能够访问的数据应受用户权限限制。访问范围校验、诊断记录与反馈审核都可形成工程成果。

### 5.4 最小可研究版本

先选一个设备子系统和 3—5 类经现场确认的故障，完成一条从告警触发、证据查询、知识检索到人工反馈的流程。先建设可重复回放的离线场景，再接入在线页面。

资料至少包括设备或点位清单、选定故障相关的手册或排查规程，以及经确认的故障样本。真实样本不足时，可建设明确标注的模拟场景，并分别报告模拟与真实场景结果。

## 7. 实验设计建议

### 7.1 评价对象

- **检索效果**：人工标注相关证据后评估召回、排序和来源准确性。
- **诊断效果**：候选根因命中、证据支撑程度、信息缺失时的合理处理。
- **使用效果**：排查任务正确性、任务耗时、建议可操作性。
- **工程效果**：响应时间分布、工具调用次数、单次成本、接口失败后的行为。

### 7.2 对照与消融

| 方案 | 要回答的问题 |
|---|---|
| 当前规则告警加固定排查模板 | 现有系统作为基线能达到什么水平？ |
| 大模型加结构化告警摘要 | 语言模型本身提供多少帮助？ |
| 大模型加普通文档检索 | 通用知识检索带来多少改善？ |
| 加入设备、时间和依赖约束 | 领域证据组织是否有效？ |
| 再加入补充工具查询及证据校验 | 查询和校验分别带来何种收益与成本？ |

比较时固定或明确报告模型版本、数据划分、工具权限与计算预算；对关键组件分别移除后复测，避免把多个变化的收益全部归给某一个设计。

### 7.3 数据与标注

以独立故障事件划分案例库和评估集，避免同一事件的改写问题同时出现在两侧。评估时只提供故障发生当时可获得的资料，并保留资料版本与时间。

根因和可接受措施应由领域人员确认。开放式建议可以有多个正确答案，采用明确评分规则，并记录评审分歧。研究论文中的语义相似度、模型评分或用户满意度可作为辅助信号。

先用一小批场景确认流程和评分标准，再依据故障覆盖及误差分析确定正式评估规模；本次不把某个任意样本数量作为毕业标准。

## 8. 选题取舍与下一步

**数据和手册较齐全时**，优先选择多源证据辅助诊断。先读 A 了解工具增强方法，再读 B 了解故障知识组织，参考 D、E 设计效果评估。

**真实故障样本有限、规则需求容易获得时**，可以选择《面向设备监控的自然语言告警规则生成与回放验证方法研究》。参考 C 的语言解析与确定性处理分工，围绕语义正确性、歧义处理、规则冲突和回放结果展开。

建议与导师确认：论文偏系统工程还是方法研究；可获得哪些真实故障和设备资料；允许的模型部署方式及计算预算；预计可投入时间。随后再确定贡献点、文献比较范围和实验规模。
