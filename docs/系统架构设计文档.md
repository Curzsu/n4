# N4-Monitor 系统架构设计文档

## 一、文档概述

本文档对 N4-Monitor 系统当前所采用的框架与技术栈进行系统梳理，绘制系统整体框架图，并给出未来面向分布式/微服务的演进架构。

N4-Monitor 是一个面向设备点位数据的实时监控与告警平台，核心能力包括：

- 采集现场设备（如 SPM32 等电能/环境监测终端）通过 MQTT 上报的点位数据；
- 经 Kafka 缓冲后，由 Flink 流处理引擎进行实时阈值评估与告警生命周期管理；
- 告警状态在 Redis 中实时维护，并通过 WebSocket 推送至前端大屏；
- 历史告警与点位全量事件数据持久化到 TDengine 时序数据库；
- 设备元数据与告警规则配置存储于 MySQL；
- 通过 FUXA 提供图形化组态监控视图（iframe 嵌入）。

## 三、系统整体框架图

### 3.1 当前架构（单体 + 内嵌流处理）

> **说明：**当前 Flink 作业运行在 Spring Boot 进程内的守护线程中，并非独立 Flink 集群部署。
> 工程为 Maven 多模块：`monitor-common`（共享模型）、`monitor-flink-job`（Flink 作业，可独立部署）、
> `monitor-backend`（Spring Boot Web 后端）。Flink 任务通过 Jedis 直连 Redis，因为 Flink 运行时
> 无法使用 Spring 的 `RedisTemplate`。仓库另提供 `docker compose --profile flink` 编排，可将作业
> 切换为独立 Flink 集群运行（与内嵌模式互斥，详见 docker-compose.yml 注释）。

### 3.2 数据流主链路（端到端）

```
设备 --MQTT(niagara_send/#)--> EMQX --规则引擎/Kafka桥接--> Kafka(mqtt-push-kafka) -> Flink(规则评估)
    -> Redis(alarm:active / alarm:latest) + Pub/Sub
    -> [通知通道] Spring WebSocket -> 前端大屏实时刷新
    -> [实时通道] TDengine alarm_realtime (告警生命周期事件)
    -> [事件通道] TDengine alarm_event (每个处理帧全量持久化, Flink 实时发布 + 后端批量写入)
    -> MySQL (设备/规则元数据, 前端配置读写)
    -> FUXA (图形化组态, 独立订阅 MQTT)
```

### 3.3 告警生命周期状态机

Flink中维护的告警状态流转：

```
                    ┌────────────────────────────────────────┐
                    │                                        │
                    ▼                                        │
   ┌─────────┐  isAlarm   ┌─────────┐  isAlarm(同级别)  ┌──────────┐
   │ (无记录) │ ────────▶  │  start  │ ───────────────▶│ continue │
   └─────────┘            └────┬────┘                  └────┬─────┘
                              │                             │
                              │ isAlarm(升级,如High->High-High)
                              │   关闭旧阶段(end) + 开启新阶段(start)
                              │                             │
                              │                     恢复正常 │
                              │                             │
                              │                             ▼
                              │             ┌──────────────────────────────────┐
                              │             │ 恢复分支:                         │
                              │             │  - 已Ack: 移除active + 通知前端清除 │
                              │             │  - 未Ack: 冻结记录                 │
                              │             │    (stage=end)                   │
                              │             └──────────────────────────────────┘
                              │
                              ▼
                        持久化到 TDengine alarm_realtime
                        (start / continue / end / 升级 各事件)
                        每个处理帧另经 alarm:persist 发布，
                        后端批量写入 TDengine alarm_event
```

## 四、核心组件职责

### 4.1 接入与编排

| 组件 | 职责 |
|------|------|
| **EMQX** | MQTT Broker，承接现场设备遥测上报，支持通配订阅、TLS、共享订阅 |
| **Node-RED** | 不参与 FUXA 设备发现或 FUXA 工程写入；FUXA 方舱 MQTT Client 由 N4 后端按方舱查看会话启停。 |
| **FUXA** | 图形化组态平台，后端通过 REST API（`/api/project`、`/api/projectData`）克隆模板设备并替换 tag 的 MQTT topic，FUXA 设备直接订阅 MQTT 渲染视图 |

### 4.2 流处理与告警

| 组件 | 职责 |
|------|------|
| **AlarmProcessingJob** | Flink 作业入口（`monitor-flink-job` 模块）：`KafkaSource` 消费 `mqtt-push-kafka`（由 EMQX 规则引擎 `mqtt_to_kafka` 桥接写入），`keyBy(path)` 按点位分键后逐条评估 |
| **AlarmProcessFunction** | 核心算子（编排层）：解析元数据 -> 路由评估 -> 延迟确认（pending）-> start/continue/end/升级生命周期管理；规则定义与点位元数据经每个 subtask 的 TTL 缓存（60s，含负缓存，按 keyBy 天然分片）读取，减少每帧串行 Redis 往返；具体执行委托给四个协作者：`RuleEvaluator`（阈值/枚举评估 + 死区门）、`RedisStateStore`（Redis 读写与发布）、`PointMetaParser`（元数据/path 解析）、`ConsoleFormatter`（控制台输出）。行为由 57 个特征测试钉死 |
| **FlinkJobRunner** | `monitor-backend` 的 `CommandLineRunner`，Spring Boot 启动后在守护线程拉起 Flink 作业，随容器生命周期启停 |

### 4.3 存储与同步

| 组件 | 职责 |
|------|------|
| **Redis** | 三类数据：① 规则缓存（`alarm:rules:numeric`、`alarm:rules:enum`、`alarm:point:rule`）；② 实时状态（`alarm:latest` 最新值、`alarm:active` 活跃告警）；③ Pub/Sub 通道（`alarm:notifications`、`alarm:realtime`、`alarm:persist`） |
| **TDengine** | 两张超级表：`alarm_realtime`（告警生命周期事件，由 `AlarmRealtimeListener` 实时写入）；`alarm_event`（每个处理帧全量持久化，由 Flink 发布 `alarm:persist`、后端 `AlarmPersistenceListener` 攒批写入）。历史快照表 `alarm` 已废弃：不再创建、不再写入，存量数据保留。采用 REST 模式（`jdbc:TAOS-RS`）免原生库依赖 |
| **MySQL** | 元数据：`device`、`product`、`monitor_point`、`point_deployment`、`alarm_rule_numeric`、`alarm_rule_enum`。通过 MyBatis Mapper 访问 |

### 4.4 实时推送

| 组件 | 职责 |
|------|------|
| **AlarmNotificationListener** | 订阅 `alarm:notifications`，收到 Flink 发布的告警后，读取 `alarm:active` 全量聚合（summary/severity/hourly），组装后通过 `AlarmWebSocketHandler.broadcast()` 推送所有前端客户端 |
| **AlarmRealtimeListener** | 订阅 `alarm:realtime`，反序列化 `PointAlarmState`，调用 `TdengineSyncService.writeRealtimeAlarm()` 异步写入 TDengine |
| **AlarmPersistenceListener** | 订阅 `alarm:persist`，接收 Flink 发布的每个处理帧，入有界批量缓冲区；`TdengineSyncService.flushPersistenceBatch()` 每秒批量写入 `alarm_event` 表 |
| **AlarmWebSocketHandler** | 管理 WebSocket 会话集合（`ConcurrentHashMap`），`/ws/alarm` 端点，per-session 同步发送防止并发写异常 |

## 五、未来分布式设计架构

当前系统为**单体应用 + 内嵌 Flink**的部署形态，适合单站点、中等数据量场景。当设备规模增长、多站点接入、高可用要求提升时，需向分布式/微服务架构演进。

### 5.1 演进目标

- **水平扩展：** 告警处理能力随设备数线性扩展（Flink 作业并行度 > 1）
- **高可用：** 消除单点，服务多实例 + 流处理作业分布式部署
- **多站点接入：** 区分边缘接入与中心聚合
- **治理能力：** 注册发现、配置中心、网关、限流熔断、链路追踪

### 5.3 演进关键点

| 维度 | 当前（单体） | 未来（分布式） |
|------|-------------|---------------|
| Flink 部署 | 默认内嵌 Spring Boot 守护线程；`keyBy(path)` 分区 + `parallelism=4`（配置项 `alarm.flink.parallelism`）；亦可经 `docker compose --profile flink` 独立集群运行 | 独立 Flink 集群，RocksDB 状态 + Checkpoint，多 TaskManager 水平扩展 |
| 告警状态 | Redis `alarm:active` 读-改-写（`keyBy(path)` 保证同点位串行） | Redis Cluster；或 Flink Managed Keyed State（需重新设计去重） |
| MQTT 接入 | 单 EMQX | 边缘 EMQX + MQTT Bridge 汇聚到中心，或 EMQX 集群 |
| 应用部署 | 单 Spring Boot 进程 + 前端 Nginx 容器 | 微服务拆分 + Nacos 注册 + Gateway 统一入口 |
| 配置管理 | `application.yaml` + 根目录 `.env`（环境变量覆盖，docker compose 与本地共享） | Nacos Config 动态配置（规则热更新无需重启） |
| 容错 | 单点，故障全损 | Sentinel 熔断 + 多实例 + K8s 自愈 |
| 规则同步 | 启动加载 + CRUD 触发 MySQL -> Redis 同步 | Nacos 配置中心 + 规则服务 API，Flink 侧感知变更 |

> **并行度说明：** 作业已按 `keyBy(path)` 分区，同一 `path` 的消息恒路由到同一并行
> 实例，`alarm:active` 的读-改-写在单作业内无竞态；`parallelism` 上限为 Kafka topic
> 分区数。约束在于**同一 topic 同时只能有一个消费组实例在跑**：内嵌作业与
> `--profile flink` 独立集群互斥，切换时须先停一侧，否则分区被瓜分导致告警随机丢失。

## 六、MQTT 方案对比：EMQX vs mica-mqtt

本项目在设备接入层需要一个 MQTT Broker。当前选型为 **EMQX**。下面对比 EMQX 与 **mica-mqtt** 两种方案，并说明 mica-mqtt 为何不适用。

### 6.1 两者定位

- **EMQX：** 基于 Erlang/OTP 的大型分布式 MQTT 消息服务器，定位为**企业级 MQTT Broker**，独立部署，提供完整的 MQTT 协议实现、集群、规则引擎、桥接能力。
- **mica-mqtt：** 基于 Java（Solon / Spring Boot）的**轻量级嵌入式 MQTT 组件**，定位为应用内嵌的 MQTT 客户端/小型 Broker，强调低门槛、易集成、单机小规模场景。

### 6.2 能力对比

| 维度 | EMQX | mica-mqtt |
|------|------|-----------|
| **定位** | 企业级独立 MQTT Broker | 嵌入式轻量 MQTT 组件（客户端/小 Broker） |
| **实现语言** | Erlang/OTP | Java |
| **连接规模** | 单机百万级，集群千万级 | 单机数千~数万级（受 JVM 与实现限制） |
| **集群能力** | 原生集群，节点自动发现与路由 | 无原生集群，单机为主 |
| **MQTT 协议完整度** | MQTT 3.1/3.1.1/5.0 全协议栈 + MQTT-SN | MQTT 3.1.1 为主，5.0 特性支持有限 |
| **共享订阅** | 完整支持（`$share/group/topic`） | 支持有限 |
| **规则引擎** | 内置 SQL 规则引擎，可直接桥接 Kafka/HTTP/DB | 无规则引擎，需自行编码 |
| **桥接/集成** | 原生 Kafka 桥接、MQTT 桥接、Webhook | 需自行实现 |
| **TLS/安全** | 完整 TLS、双向认证、ACL、PSK | 基础 TLS 支持 |
| **EMQX 桥接 Kafka** | 原生支持，可替代当前 Kafka Producer 链路 | 不支持 |
| **运维监控** | Dashboard、Prometheus 指标、慢订阅分析 | 基本无 |
| **多站点边缘汇聚** | MQTT Bridge / 集群原生支持 | 不适合 |
| **高可用** | 集群 + 共享订阅，Broker 无单点 | 单进程，应用挂则 Broker 挂 |
| **与 FUXA 共存** | 独立 Broker，FUXA 直接订阅 | 若嵌入后端进程，FUXA 需连后端端口，耦合 |

### 6.3 mica-mqtt 不适合本项目的原因

结合 N4-Monitor 的实际架构与未来演进需求，mica-mqtt 方案不适用，具体原因如下：

**1. 承担角色错配 —— 本项目需要独立 Broker 而非嵌入式组件**

本系统中 MQTT Broker 是**多消费方共享的基础设施**：
- 现场设备（生产者）上报遥测到 `niagara_send/#`；
- EMQX 规则引擎（`mqtt_to_kafka`）桥接转发至 Kafka；
- FUXA 设备**直接订阅 MQTT** 渲染组态视图；
- Kafka 生产链路（由 EMQX 规则引擎 + Kafka 桥接把 `niagara_send/#` 消息投递到 `mqtt-push-kafka`，开发调试时可用脚本直接发 Kafka）。

这意味着 Broker 必须是**独立长驻、多客户端并发订阅**的服务。mica-mqtt 作为嵌入式组件，若嵌入 Spring Boot 后端进程，则 FUXA、Node-RED、设备都要连接后端端口，Broker 生命周期与应用耦合——后端重启即导致全场设备断连与组态中断。EMQX 独立部署则无此问题。

**2. 连接规模与集群能力不足，无法支撑未来分布式演进**

第五节的分布式架构明确规划了"边缘 EMQX + MQTT Bridge 汇聚中心"的多站点接入形态。mica-mqtt 无原生集群、无 MQTT Bridge 桥接、单机连接规模有限，无法满足多站点汇聚与水平扩展。EMQX 的集群与共享订阅能力是演进的基础设施前提。

**3. 缺少规则引擎与 Kafka 桥接，需额外开发**

当前数据链路为 `EMQX -> Kafka`，EMQX 通过**规则引擎（`mqtt_to_kafka`）+ Kafka 桥接**把 `niagara_send/#` 的 MQTT 消息直接投递到 `mqtt-push-kafka` topic，无需编写独立采集服务。mica-mqtt 无此能力，需自行开发 MQTT 订阅 + Kafka Producer 转发组件，增加维护成本与故障点。

**4. 运维可观测性缺失**

EMQX 提供 Dashboard、慢订阅分析、Prometheus 指标导出，便于排查设备连接异常与消息积压。这对工业监控场景（需定位是设备掉线还是链路问题）至关重要。mica-mqtt 基本无运维观测手段。

### 6.4 结论

| 场景 | 推荐方案 |
|------|---------|
| 本项目（多消费方、多站点、需 Kafka 桥接、需高可用） | **EMQX** ✅ |
| 单体小应用、少量内嵌 MQTT 客户端、无独立 Broker 需求 | mica-mqtt |

**mica-mqtt 适合"应用内嵌一个轻量 MQTT 客户端/小 Broker"的场景，而 N4-Monitor 需要的是"独立、多消费方、可集群、可桥接 Kafka 的企业级 MQTT Broker"。两者定位不同，mica-mqtt 在连接规模、集群、桥接、高可用、可观测性等关键维度均无法满足本项目当前架构与未来分布式演进的需求，因此不适用。当前 EMQX 选型正确，建议在分布式演进中继续沿用 EMQX 集群 + 边缘 Bridge 方案。**
