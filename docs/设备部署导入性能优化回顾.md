# Device Deployment 导入性能优化回顾

## 1. 文档目的

本文回顾 `Device Deployment` 导入 CSV/ZIP 文件从问题发现、性能定位到代码优化的完整过程，说明每次调整解决了什么问题、保留了哪些业务行为，以及当前还可能存在的优化方向。

适用范围：

- Device Deployment 页面导入 CSV 文件或 ZIP 压缩包。
- 导入流程中的 Preview 和 Confirm Import。
- 设备、点位、报警规则及报警编码关联的持久化过程。

## 2. 最终结论

这次导入变慢的核心不是某一条 SQL 本身执行特别慢，而是大量逐条数据库写入叠加形成的典型 **N+1 写入问题**，也可以称为 **数据库往返次数过多**。

本次最高 ROI 的处理方式是：

1. 新点位在已有的批量插入中直接写入 `alarm_code`，不再插入后逐条补写。
2. 已有点位的报警编码只收集真正发生变化的记录，再按最多 500 条一批使用 `CASE ... WHERE IN (...)` 批量更新。
3. 点位模板的报警编码改为批量更新。
4. 设备模板、设备部署和点位模板的报警编码相同时跳过写入。
5. 保持原有事务边界和导入结果不变，Redis 同步仍在数据库事务提交后异步执行。

这几项改动直接减少了导入确认阶段的数据库写操作数量，是优先缩短实际导入时间最有效的一组改动。

## 3. 问题现象与基线

### 3.1 用户侧现象

用户将文件拖入 Device Deployment 的 Import 区域，点击 `Confirm Import` 后需要等待较长时间。对于提供的测试样例，用户反馈实际等待时间仍可能达到 30 秒以上。

### 3.2 样例规模

此前性能设计记录中的样例约有：

- 2,488 行 CSV 数据。
- 约 1,662 行包含报警配置。
- Preview 请求约 6.6 秒。
- Confirm Import 请求约 36.3 秒。

以上数据来自同一份导入性能设计记录，适合作为问题定位时的基线，但不能直接当作所有数据库环境下的固定耗时。

### 3.3 为什么一次操作会出现两条审计记录

当前前端流程本身包含两个请求：

| 操作 | 请求参数 | 是否写数据库 | 作用 |
| --- | --- | --- | --- |
| Preview | `dryRun=true` | 否 | 解析、校验并生成导入预览 |
| Confirm Import | `dryRun=false` | 是 | 再次解析、校验并执行正式持久化 |

因此，一次正常的用户操作产生两条审计记录是预期行为，并不代表文件被导入了两次。

此前看到的两条记录：

- 记录 111：约 4,945 ms，参数为 `dryRun=true`。
- 记录 112：约 5,146 ms，参数为 `dryRun=false`。

它们分别对应 Preview 和 Confirm Import。后续又将审计 operation 名称区分为 `Preview deployment files` 和 `Import deployment files`，避免两条记录在页面上看起来完全重复。

## 4. 原始导入流程

正式导入由 `DeploymentTransferService.importFiles()` 负责，主要流程如下：

1. 读取上传的 CSV 文件或 ZIP 中的 CSV 文件。
2. 解析 CSV 行并校验必填字段、重复路径、设备模板和点位模板。
3. 读取已有设备模板、点位模板、设备部署、点位部署及导航节点。
4. 在内存中建立索引并生成设备计划、点位计划和报警规则计划。
5. 根据 `dryRun` 判断：
   - Preview 直接返回统计结果，不进入数据库写入阶段。
   - Confirm Import 进入事务内的持久化阶段。
6. 正式导入依次处理设备、点位、报警规则和报警编码关联。
7. 数据库事务提交后，异步触发报警规则和点位规则的 Redis 同步。

原有代码已经具备部分批处理能力，例如点位部署插入使用批量写入，导入点位的已有记录查询也按批次处理。因此，优化重点不是推翻整个导入流程，而是针对报警编码关联中仍然存在的逐条更新。

## 5. 性能根因定位

### 5.1 主要问题：逐点更新报警编码

原始实现中，`persistAlarmCodeLinks()` 会针对导入行逐个处理点位报警编码。对于每一个需要关联报警的点位，都可能单独执行一次按 `n4_address` 更新的 SQL。

当样例中约有 1,662 行带报警配置时，即使单条 SQL 只耗费很短时间，累计的数据库连接、网络往返、事务日志和锁开销也会明显放大总耗时。

这类问题的典型工程术语是：

- N+1 writes：一批导入数据被拆成大量单行写入。
- Excessive database round trips：应用和数据库之间往返次数过多。
- Chatty persistence layer：持久化层过于频繁地和数据库交互。

因此，问题不宜简单归类为“某条慢 SQL”。更准确的描述是：**单条语句未必慢，但语句数量过多造成整体导入变慢**。

### 5.2 次要问题：重复解析和校验

Preview 和 Confirm Import 是两个独立请求，确认阶段会再次读取和解析文件，并重新执行校验和计划生成。

这会带来两部分额外成本：

- 用户点击 Preview 后，Confirm 仍然需要再次完成解析和校验。
- 审计日志会记录两次请求的耗时，用户容易将两次等待时间理解为一次导入很慢。

本轮优先处理数据库写入，因为它直接影响正式导入的实际持久化时间；Preview 与 Confirm 的结果复用属于下一阶段优化。

### 5.3 不是当前首要问题的部分

- 点位已有记录查询已经按最多 5,000 个地址分批查询，避免生成无限大的 `IN` 条件。
- 新点位插入已经按最多 500 条进行批量写入。
- Redis 同步在数据库事务提交后异步调度，不是当前 HTTP 请求中最主要的同步等待点。
- 设备数量通常远少于点位数量，设备级别的单条更新不是本轮最高 ROI 目标。

## 6. 优化历程

### 6.1 阶段一：建立 Preview 和导入统计基础

提交：`2aa589f`

这一阶段不是纯性能优化，但为后续定位提供了必要基础：

- 明确区分 Preview 和正式导入。
- 增加导入统计和设备部署预览明细。
- 前端在确认导入前展示解析结果。
- 后端通过 `dryRun` 控制 Preview 是否进入持久化阶段。

这一步让导入流程变得可观察，也暴露出 Preview 和 Confirm 是两次独立执行。

### 6.2 阶段二：分析并确定高 ROI 方案

提交：`fe75bf2`、`647a122`

这一阶段形成了性能设计和实施计划，确定以下原则：

- 不改变 CSV/ZIP 导入接口。
- 不改变现有校验规则和导入结果。
- 不改变事务边界。
- 优先减少 MySQL 往返次数。
- 只更新发生变化的报警编码。
- 批量 SQL 必须有上限，避免生成无界 SQL。
- 暂不引入异步导入任务和进度轮询。

### 6.3 阶段三：优化点位部署报警编码写入

提交：`e009646`

#### 新点位

优化前，新点位先进入批量插入，报警编码可能还需要后续逐条补写。

优化后，服务在构造 `PointDeployment` 时就设置解析出的报警编码，直接放入原有 `insertBatch()` 缓冲区。

结果是：

- 新点位的报警编码随批量插入一次完成。
- 不再为新点位执行额外的逐条报警编码更新。

#### 已有点位

优化后只收集满足以下条件的已有点位：

- 导入结果中确实解析出了报警编码。
- 导入的报警编码与数据库现有值不同。

然后每 500 条组成一个批次，通过基于 `n4_address` 的 `CASE` 更新一次性写入。

这种方式保留了原有按地址匹配的业务语义，但把大量单行 UPDATE 减少为少量批量 UPDATE。

### 6.4 阶段四：减少重复报警编码写入

提交：`e637814`

这一阶段进一步处理设备模板、点位模板和设备部署层面的报警编码关联：

- 建立内存映射，先拿已有对象的当前报警编码进行比较。
- 设备模板报警编码相同时跳过更新。
- 设备部署报警编码相同时跳过更新。
- 点位模板报警编码只收集变化项，并按最多 500 条批量更新。
- 保留“导入文件没有报警编码时不清空原值”的既有行为。

这样可以避免重复导入同一文件时，数据库再次接收大量没有实际变化的 UPDATE。

### 6.5 阶段五：补充审计可观测性

提交：`4e10206`

这一阶段不改变导入性能，但解决了性能排查时的歧义：

- Preview 审计 operation：`Preview deployment files`。
- Confirm Import 审计 operation：`Import deployment files`。

以后可以直接从 Audit Logs 判断每条记录属于预览还是正式导入，不需要再查看隐藏的 `dryRun` 请求参数。

## 7. 优化前后对比

| 写入对象 | 优化前 | 优化后 | 直接收益 |
| --- | --- | --- | --- |
| 新点位报警编码 | 插入后可能逐条补写 | 随 `insertBatch()` 一起写入 | 额外更新次数降为 0 |
| 已有点位且编码变化 | 每个点位一条 UPDATE | 每最多 500 个点位一批 | 从 N 次降为最多 `ceil(N / 500)` 次 |
| 已有点位且编码不变 | 可能重复更新 | 跳过 | 不产生无效写入 |
| 导入行没有报警编码 | 不能覆盖原有值 | 继续不清空原有值 | 保持兼容行为 |
| 点位模板报警编码 | 逐项更新 | 变化项分批更新 | 减少往返次数 |
| 设备模板/设备部署报警编码 | 逐项更新 | 相同值跳过 | 减少无效 UPDATE |
| Redis 同步 | 事务提交后异步调度 | 保持不变 | 不改变现有时序 |

以约 1,662 条带报警配置的样例为例，如果这些记录全部是已有点位且报警编码全部发生变化，点位报警编码更新理论上可以从约 1,662 条单独 UPDATE 降到最多 4 个批次。

实际批次数会受到以下因素影响：

- 有多少点位是新建记录。
- 有多少已有点位的报警编码真的发生变化。
- 不同 CSV 行最终映射到多少个点位模板、设备模板和设备部署。

因此，上述数字是 SQL 数量的理论上限估算，不等同于固定的端到端耗时承诺。

## 8. 数据和业务行为保护

本轮优化没有改变以下行为：

1. Preview 不写入部署数据。
2. Confirm Import 仍然在原有事务边界内执行。
3. CSV/ZIP 解析、字段校验、重复路径校验保持不变。
4. 已有点位的元数据变更判断保持不变。
5. 导入文件没有报警编码时，不清空数据库中已有的报警编码。
6. 报警规则仍然在数据库事务内持久化。
7. Redis 同步仍然在事务提交后执行。
8. 批量 SQL 每批最多 500 条，避免单次 SQL 无界增长。

## 9. 验证情况

### 9.1 自动化测试

`DeploymentTransferServiceTest` 当前覆盖了以下场景：

- 新点位批量插入时带有正确报警编码。
- 已有点位报警编码变化时进入批量更新。
- 报警编码未变化时不触发更新。
- 导入文件没有报警规则时不清空原有报警编码。
- 大批量点位已有记录查询按批次执行。
- 导入提交后 Redis 同步不阻塞导入响应。
- 不同系统路径下的同名设备和报警关联保持隔离。

当前导入核心回归测试结果为 **14/14 通过**。

### 9.2 实际接口验证

在本地服务上执行过一次 `dryRun=true` 的预览请求：

- 请求返回成功。
- 不写入部署数据。
- 最新审计记录显示为 `Preview deployment files`。

这次验证同时确认了 Preview/Confirm 审计名称区分已经在实际后端进程中生效。

### 9.3 结果解读边界

后续性能对比必须保证以下条件一致：

- 相同的 CSV/ZIP 文件。
- 相同的数据库数据量和已有记录状态。
- 相同的数据库、Redis 和网络环境。
- 分别记录解析、查询、持久化、事务提交和 Redis 调度阶段耗时。

仅比较两条审计日志的总耗时，无法判断具体是解析慢、SQL 慢、数据库锁等待，还是前端两次请求叠加造成的等待。

## 10. 当前仍可能存在的瓶颈

本轮已经处理了最高收益的报警编码逐条写入，但以下部分仍可通过后续 profiling 决定是否优化：

1. Preview 和 Confirm 会重复解析、校验和构建导入计划。
2. `persistAlarmRules()` 仍按报警计划逐条写入报警规则；如果报警规则数量很大，可能成为新的写入热点。
3. 设备和点位的元数据更新仍需根据实际变更逐条执行。
4. 当前审计日志只有整个请求耗时，缺少分阶段耗时。

## 11. 后续优化建议（按 ROI 排序）

### 11.1 第一优先级：复用 Preview 结果

可以让 Preview 生成一个短期有效的导入会话或导入计划，Confirm Import 只提交该计划，而不是重新解析同一份文件。

建议至少绑定以下信息：

- 当前用户和权限。
- 文件内容哈希或上传对象 ID。
- 预览结果的有效期。
- 导入模板和数据库版本信息。
- Confirm 时的再次权限校验。

这项优化最有可能减少用户感知到的两次解析和校验等待，但需要额外处理过期、重复提交、文件被替换和权限变化等安全问题。

### 11.2 第二优先级：增加分阶段性能指标

建议分别记录：

- 文件读取和解压耗时。
- CSV 解析耗时。
- 数据加载和已有记录查询耗时。
- 设备/点位计划构建耗时。
- 报警规则构建耗时。
- 数据库持久化耗时。
- 事务提交耗时。
- Redis 同步排队耗时。

这样可以判断下一轮应该继续优化 SQL，还是应该优化文件解析、对象构建或事务等待。

### 11.3 第三优先级：批量写入报警规则

如果分阶段指标证明报警规则写入仍然占用较多时间，再考虑为枚举报警规则和数值报警规则增加批量 INSERT。该改动涉及规则主键、重复规则、失败回滚和数据库参数上限，需要在报警规则数据量达到瓶颈后再实施。

### 11.4 第四优先级：异步导入和进度展示

如果文件规模继续增长，可以将正式导入改为异步任务并提供进度查询。这主要改善用户体验和请求超时风险，不一定会缩短数据库实际执行时间，因此优先级低于减少数据库往返。

## 13. 总结

这次优化的关键思路不是简单地把某条 SQL 改快，而是先找到导入过程中的高频写入点，再将“逐条写入”改成“只写变化项，并按上限批量写入”。

当前实现已经解决了报警编码关联中最典型的 N+1 写入问题，同时保留了原有校验、事务和数据兼容行为。下一步如果还需要继续缩短用户等待时间，应优先通过分阶段指标确认剩余时间主要消耗在重复解析，还是报警规则批量写入，再决定是否继续扩大改动范围。
