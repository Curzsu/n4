## 一、项目概述与部署形态

N4-Monitor 是面向 N4（Niagara）设备的监控与告警平台，当前部署形态为**单体应用 + 内嵌流处理**：

| 组成 | 技术 | 说明 |
|---|---|---|
| 后端 | Spring Boot 4.0.7（Java 21） | 提供 Web API + WebSocket，进程内以守护线程拉起 Flink 告警作业 |
| 流处理 | Flink 2.2.1（默认内嵌，可独立集群） | `monitor-flink-job` 模块，规则评估（阈值/死区/延迟确认/级别升降级） |
| 前端 | Vue 3 + Vite + Element Plus | 监控大屏，构建产物由 Nginx 托管并反代 API/WebSocket |
| MQTT | EMQX（独立中间件） | 承接设备遥测（`niagara_send/#`），FUXA 直接订阅渲染 |
| 消息 | Kafka | 流处理输入（`mqtt-push-kafka`，由 EMQX 规则引擎桥接写入） |
| 缓存/状态 | Redis | 规则缓存、实时状态、Pub/Sub 通知 |
| 时序库 | TDengine（REST 模式） | 告警生命周期事件 + 全量帧持久化 |
| 业务库 | MySQL | 设备/产品/点位/规则元数据 |
| 组态 | FUXA（独立容器） | 图形化组态，通过 MQTT 订阅渲染 |

**数据主链路（生产环境）：**

```
现场设备 --MQTT(niagara_send/#)--> EMQX
    --规则引擎(rule: mqtt_to_kafka) + Kafka桥接(action: push_kafka)--> Kafka(mqtt-push-kafka)
    --> Flink(规则评估)
    -> Redis(alarm:active / alarm:latest) + Pub/Sub
    -> [通知通道] Spring WebSocket -> 前端大屏实时刷新
    -> [实时通道] TDengine alarm_realtime（告警生命周期事件）
    -> [事件通道] TDengine alarm_event（每个处理帧全量持久化）
    -> MySQL（设备/规则元数据）
    -> FUXA（图形化组态，独立订阅 MQTT）
```

> **数据链路说明（已按服务器实际配置核实）：**
> - 生产数据流是 **设备 → EMQX → Kafka → Flink**：现场设备通过 MQTT 上报到 EMQX 的 `niagara_send/#` 主题，EMQX 规则引擎（规则 `mqtt_to_kafka`，`SELECT * FROM "niagara_send/#"`）通过 Kafka 桥接 action（`push_kafka`，connector `n4-kafka-producer`）把消息写入 Kafka topic **`mqtt-push-kafka`**，Flink 作业再消费该 topic。
> - **开发测试例外**：`test-producer/kafka_producer_single.py` 是开发调试脚本，为绕过设备/EMQX 直接向 Kafka 发送测试数据（topic 为 `kafka-test`，仅调试用），**不代表生产链路**。生产链路一律经 EMQX 桥接。

## 三、端口与网络拓扑

### 3.1 端口清单

| 端口 | 用途 | 归属 |
|---|---|---|
| 80 | N4-monitor 前端（对外） | Nginx 容器（host 模式） |
| 8088 | 后端 API + WebSocket（对外/反代目标） | 后端容器（host 模式，由 `SERVER_PORT` 统一控制，默认 8088） |
| 1881 | FUXA 图形化组态（浏览器 iframe 直连） | FUXA 容器 |
| 3000 | Gitea（自建代码仓库） | Gitea |
| 3306 | MySQL（业务库 n4_monitor） | 中间件 |
| 6379 | Redis | 中间件 |
| 9092 | Kafka | 中间件 |
| 6041 | TDengine REST（库 n4） | 中间件 |
| 1883 | EMQX MQTT（默认端口，按实际） | 中间件 |
| 8081 | Flink Web UI（**仅本机回环** `127.0.0.1:8081`，需 SSH 隧道访问） | 独立 flink 集群（profile） |

### 3.2 网络模式：host 网络（关键）

后端与前端容器均使用 **`network_mode: host`**，共享宿主机网络栈：

- **好处**：容器内 `localhost` == 宿主机回环。当 Redis/Kafka/MySQL 等中间件与容器在同一台机器时，走回环（loopback）而非 Docker 网桥/NAT，延迟更低，避免"明明本机却走网络"的性能问题。
- **影响**：host 模式下**没有 compose 服务名 DNS**（不能像 `n4-monitor-backend:8088` 这样互相访问）。因此前端 Nginx 反代上游写死 `127.0.0.1:${BACKEND_PORT}`；后端访问中间件用 `.env` 里的地址（同机建议 `127.0.0.1` 或 localhost）。
- **FUXA 例外**：前端浏览器加载 FUXA iframe 用的是 `.env` 里 `FUXA_BASE_URL` 的**公网/可访问地址**（如 `http://47.121.30.136:1881`），因为那是浏览器直连，不是容器间调用。

### 3.3 端口全局统一开关（改一处全生效）

后端端口是**单一开关**，改 `.env` 里的 `SERVER_PORT`（默认 `8088`）即可，所有消费方自动跟随：

| 消费方 | 机制 |
|---|---|
| docker-compose 后端映射 | `${SERVER_PORT:-8088}` |
| 前端 Nginx 反代上游 | nginx.conf 是模板，容器启动时经 **envsubst** 用 `${BACKEND_PORT}`（取值同 `SERVER_PORT`）渲染 |
| Spring Boot server.port | `application.yaml` 里 `${SERVER_PORT:8088}` |
| 本地开发 vite 代理 | vite.config.ts 的 `VITE_BACKEND_PORT || '8088'` |

> 注意：改 `SERVER_PORT` 后，`docker compose up -d` 重建后端与前端即可；`EXPOSE 8088` 只是说明性声明，host 模式下无实际映射作用。

## 四、环境变量配置（.env）

### 4.1 消费方与加载顺序

`.env` 文件位于**仓库根目录**，同时被两个消费方读取：

1. **docker compose**：compose 文件与 `.env` 同目录，`${VAR}` 直接插值。
2. **Spring Boot**：`application.yaml` 里 `spring.config.import: optional:file:.env[.properties]`（相对启动目录）与 `optional:file:../.env`（上一级目录），`.env` 值覆盖默认值，**OS 环境变量仍优先于 `.env`**。

> ⚠️ **安全注意**：`.env` **不纳入版本控制**——`.gitignore` 忽略 `*.env`（仅放行 `.env.example`），git 历史也已通过 filter-repo 重写清除。每台部署机需 `cp .env.example .env` 并按环境填写真实口令。**请勿把 `.env` 加入 git 跟踪/推送**：口令一旦进入 git 历史，仅删除文件无法作废，必须到服务端逐一改密轮换。

### 4.2 变量清单

| 变量 | 示例值 | 说明 |
|---|---|---|
| `MYSQL_URL` | `jdbc:mysql://127.0.0.1:3306/n4_monitor?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Shanghai` | MySQL JDBC 连接串 |
| `MYSQL_USERNAME` | `root` | MySQL 账号 |
| `MYSQL_PASSWORD` | （口令） | MySQL 口令 |
| `KAFKA_BOOTSTRAP_SERVERS` | `127.0.0.1:9092` | Kafka broker 地址 |
| `REDIS_HOST` / `REDIS_PORT` | `127.0.0.1` / `6379` | Redis 地址端口（同机建议回环） |
| `REDIS_PASSWORD` | （口令） | Redis 口令 |
| `TDENGINE_URL` | `jdbc:TAOS-RS://127.0.0.1:6041/n4` | TDengine 连接串（REST 模式，实测优于 WS；可选 WS：改为 `jdbc:TAOS-WS://127.0.0.1:6041/n4` 即可，其余不变） |
| `TDENGINE_USERNAME` / `TDENGINE_PASSWORD` | `root` / （口令） | TDengine 账号口令 |
| `FUXA_BASE_URL` | `http://127.0.0.1:1881` 或公网地址 | FUXA 服务地址（后端模板 provisioning + 前端 iframe 构建地址） |
| `ALARM_FLINK_ENABLED` | `true` | 内嵌 Flink 报警作业开关（`application.yaml` 占位符 `${ALARM_FLINK_ENABLED:true}`）。本地开发不碰报警链路可在 `.env` 置 `false`：后端不连 Kafka、不做规则评估，模板/导航/FUXA 等 CRUD 不受影响；切独立集群前置 `false` 并重建后端 |
| `ALARM_FLINK_TOPIC` | `mqtt-push-kafka` | 报警作业消费的 Kafka topic（`application.yaml` 与独立集群 `--kafka-topic` 同读此变量，自动保持一致）。联调可覆盖为 `kafka-test`；须与 EMQX 桥接目标 topic 一致 |
| `ALARM_FLINK_PARALLELISM` | `4` | 报警作业并行度（内嵌 `application.yaml` 与独立集群 `--parallelism` 同读此变量）；必须 ≤ min(CPU 核数, Kafka topic 分区数) |
| `SERVER_PORT` | `8088` | 后端端口全局开关（见 3.3） |

**docker-compose 内仍有硬编码的项**（不消费 `.env`，需要时在 compose 中调整）。`.env` 以 `application.yaml` 消费的变量为主：yaml 占位符用到的（如 `ALARM_FLINK_ENABLED`）走 `.env` 插值，compose 中有对应配置的（容器环境变量、独立集群命令行参数）跟随同一变量，没有对应配置的保持 compose 固定值。现硬编码项：

| 项 | 当前值 | 说明 |
|---|---|---|
| `TZ` | `Asia/Shanghai` | 容器时区（后端/前端/独立 Flink 集群） |
| `JAVA_OPTS` | `-Xms512m -Xmx1024m -Dfile.encoding=UTF-8` | 后端 JVM 堆参数，按宿主机内存调整 `-Xmx` |
| `VITE_FUXA_URL` | `${FUXA_BASE_URL}/home?viewName=H1_EMSB_A4_03_EM` | 前端构建期 iframe 地址（`FUXA_BASE_URL` 部分插值自 `.env`，视图名硬编码） |
| Flink 独立集群内部参数 | checkpoint 60s/EXACTLY_ONCE、固定延迟重启（5 次/10s）、TaskManager slot=4、JVM process size 等 | 仅 `--profile flink` 使用，写在 compose `FLINK_PROPERTIES` 与资源限制中 |
| 独立集群 `--group-id` | `n4-flink-alarm-processor-prod` | 与内嵌组（`n4-flink-alarm-processor`）刻意区分；两种模式互斥运行，无需从 `.env` 配置 |

## 五、中间件部署要点

中间件（MySQL/Redis/Kafka/TDengine/EMQX/FUXA）**不在本项目 compose 内**，需提前在宿主机用各自的 docker-compose 运行（开发机位于 `/opt/<name>/`）。N4-monitor 只通过 `.env` 连接它们。要点：

- **FUXA 镜像 `frangoteam/fuxa:1.3.3`** 是手工上传的自定义镜像，公共 registry 拉不到；迁移测试机时需走 `deploy/pack.sh` 打包（`EXTRA_IMAGES` 已含）。
- **FUXA 组态数据**：FUXA 工程（`project.fuxap.db`）与用户存在挂载的 `./appdata` 目录，属**手工搭建不可再生**的配置，pack.sh 会**完整复制**；`./db`、`./logs` 属数据目录，只建空结构。
- **EMQX 配置**分两类：静态配置（`./etc` 下 `emqx.conf` 等，随包迁移）与运行时配置（Dashboard 里改的认证/规则引擎/桥接/ACL，存在 `./data`，**不迁移**，测试机需重新配置）。**注意：EMQX→Kafka 桥接属于运行时配置**——生产数据流依赖的规则 `mqtt_to_kafka` 与 Kafka 桥接（connector `n4-kafka-producer`、action `push_kafka`、topic `mqtt-push-kafka`）在测试机上需在 EMQX Dashboard 重新创建，否则设备数据不会进入 Kafka，Flink 收不到数据。
- **时区**：中间件容器建议统一 `TZ=Asia/Shanghai`，与后端、TDengine 的 `serverTimezone` 对齐，避免时间戳偏移。

## 六、构建流程细节

### 6.1 后端镜像（monitor-backend/Dockerfile）

多阶段构建，**构建上下文是仓库根目录**（Maven reactor 需要三个模块）：

1. **Stage1 builder**（`maven:3.9-eclipse-temurin-21`）：只拷 POM 先解析依赖缓存；随后拷 `monitor-common` + `monitor-flink-job` + `monitor-backend` 源码，用 **Aliyun 镜像**（`-s ./maven-settings.xml`）执行 `clean package -DskipTests`。
2. **jar 解包**：用 JDK `jar xf` 把 fat jar 解成 `BOOT-INF/classes + BOOT-INF/lib/*.jar` 的平铺目录——因为 `java -jar` 的嵌套 jar URL（`nested:...!/BOOT-INF/lib/...`）Flink 的类加载器不认，会抛 `ClassNotFoundException`。
3. **Stage2 runtime**（`eclipse-temurin:21-jre`）：`WORKDIR /app`，用 **flat classpath**（`BOOT-INF/classes` + 所有 `BOOT-INF/lib/*.jar`）直接 `java -cp ... com.n4monitor.N4MonitorApplication` 启动，而非 `-jar`。
4. **健康检查**：`bash -c "</dev/tcp/127.0.0.1/${SERVER_PORT:-8088}"` 做 TCP 探活（镜像不装 curl），start-period 60s。
5. **日志**：logback 落盘到 `logs/n4-monitor.log`（`/app/logs`），挂载命名卷 `n4-monitor-logs` 持久化；滚动策略单文件 50MB、保留 30 份、总上限 500MB。

> **Maven 镜像源说明**：Aliyun 镜像 `mirrorOf=central`（只镜像 Central）。**刻意不用 `dependency:go-offline`**——它会过度解析所有声明的依赖，命中中央仓库不存在的 RedHat 特殊版本 `jackson-mapper-asl:1.9.14.jdk17-redhat-00001` 而失败；`clean package` 只解析编译实际需要的依赖，配镜像后成功。设置文件放 `monitor-backend/maven-settings-aliyun.xml`（不放 `deploy/`，因为 `.dockerignore` 排除了 `deploy/`）。

### 6.2 前端镜像（frontend/Dockerfile）

1. **Stage1 builder**（`node:22-alpine`）：`npm ci` 装依赖（利用 layer 缓存），`npm run build` 构建 SPA（`vue-tsc -b && vite build`）。
2. **构建期注入 `VITE_FUXA_URL`**：`docker-compose.yml` 里 `n4-monitor-frontend.build.args.VITE_FUXA_URL` 来自 `.env` 的 `FUXA_BASE_URL`，浏览器直接用它加载 FUXA iframe，因此**必须是客户端可达地址**。
3. **Stage2 runtime**（`nginx:stable-alpine`）：把 `nginx.conf` 作为模板放入 `/etc/nginx/templates/default.conf.template`，官方 entrypoint 启动时用 envsubst 渲染 `${BACKEND_PORT}`。
4. **健康检查**：`wget --spider http://localhost/`（alpine 自带 busybox wget）。

### 6.3 独立 Flink 集群（可选，`--profile flink`）

默认后端内嵌运行 Flink 作业。如需独立集群，`docker compose --profile flink up -d` 会启动 `flink-jobmanager`（应用模式，容器即作业）+ `flink-taskmanager`：

- 构建上下文为仓库根，`monitor-flink-job/Dockerfile` 用 `mvn -pl monitor-flink-job -am clean package` 构建 shaded jar，放入 `/opt/flink/usrlib/alarm-job.jar`；基础镜像 `flink:2.2.1-scala_2.12-java21`，时区 Asia/Shanghai。
- 作业参数在 compose 的 `command: standalone-job --job-classname com.n4monitor.flink.AlarmProcessingJob --kafka-topic mqtt-push-kafka --group-id n4-flink-alarm-processor-prod ... --parallelism 4`。
- **Checkpoint**：`execution.checkpointing.interval: 60s`、`EXACTLY_ONCE`，状态目录挂命名卷 `flink-checkpoints`/`flink-savepoints`。
- **Web UI 无认证**，只绑 `127.0.0.1:8081`，远程需 SSH 隧道。
- **与内嵌模式互斥**：两者消费同一 Kafka topic，同时运行会瓜分分区导致告警随机丢失。**切换顺序**：先把后端 `ALARM_FLINK_ENABLED=false` 并重建后端，再起 flink profile。

### 6.4 .dockerignore 关键点

`.dockerignore` 排除了 `docs/`、`deploy/`、`材料/`、`构建数据/`、`tools/`、`outputs/`、`test-producer/`、`*.md`、`*.sql`、`*.env` 等，保证构建上下文最小化、口令不进镜像层。

## 七、标准部署步骤

### 7.1 前置条件

- Docker（建议 24+）+ Compose v2 插件（Docker 20.10+ 自带）。
- Java 21 / Maven / Node.js 仅本地开发需要（Docker 构建在镜像内完成）。
- 端口 80、8088 未被占用；中间件已就绪且连通。
- **不要用 `apt install podman-docker` 或 `docker.io`**：前者只是 podman 伪装层（compose 兼容差），后者是 Ubuntu 老版 Moby（不带 compose v2）。测试机装 Docker 官方版步骤见 deploy/README.md。

### 7.2 部署流程（开发机/服务器通用）

```bash
# 1. 获取代码
cd /opt
git clone http://47.121.30.136:3000/zhaojin/N4-monitor.git
cd N4-monitor
git checkout Xu        # 当前部署分支

# 2. 准备环境变量（.env 不入库，需从模板创建）
cp .env.example .env
vi .env                # 填真实中间件地址与口令

# 3. 构建镜像（首次较慢：后端下 Maven 依赖 + 前端 npm ci，约 5-15 分钟）
docker compose build

# 4. 后台启动
docker compose up -d

# 5. 查看状态 / 日志
docker compose ps
docker compose logs -f n4-monitor-backend
```

### 7.3 验证部署

```bash
docker compose ps                          # 两个容器 Up
docker compose logs n4-monitor-backend     # 看到 "Started N4MonitorApplication" + "N4-Monitor Alarm Processing Job"
docker exec n4-monitor-backend date        # 应为 CST / Asia/Shanghai
curl -I http://<服务器IP>/                  # 前端 200
curl http://<服务器IP>/api/monitor/nav     # 后端 API（按实际接口）
docker compose ps | grep -i health         # 健康状态 healthy
```

浏览器访问 `http://<服务器IP>/` 即可使用。

### 7.4 更新代码后重新部署

```bash
git pull
docker compose build                       # 增量构建（复用缓存）
docker compose up -d                       # 滚动更新
```

### 7.5 停止/重启

```bash
docker compose stop                        # 停止容器（保留容器与数据）
docker compose start                       # 再次启动
docker compose restart                     # 重启
docker compose down                        # 停止并移除容器（保留镜像与命名卷数据）
docker compose down -v                     # 谨慎：连同命名卷数据一起清空
```

> `down` 不会重新下载依赖/镜像（镜像已缓存，构建产物在本地镜像层），只是停止并移除容器；下次 `up -d` 直接复用。

## 八、一键迁移到测试环境（pack.sh / unpack.sh）

开发机（`/opt` 中间件 + N4-monitor）整体复制到测试机，用 `deploy/pack.sh` + `deploy/unpack.sh`。

### 8.1 迁移范围约定

- **迁移**：代码、compose 配置、N4-monitor 自建镜像、`.env`、中间件配置文件/配置目录（emqx `./etc` 等）、FUXA 自定义镜像、数据挂载目录的**空结构**。
- **不迁移**：MySQL 表数据、TDengine 时序数据、Redis 缓存、Kafka 消息、EMQX 运行时配置（`./data`）——测试机以空库/默认状态启动。

### 8.2 开发机打包

```bash
cd /opt/N4-monitor/deploy
sudo ./pack.sh          # 生成 n4-monitor-pack-<时间戳>.tar.gz
```

脚本动作：重建 N4-monitor 镜像 → `docker save` 导出 N4 自建镜像 + FUXA（`EXTRA_IMAGES`）+ 中间件官方镜像（`MIDDLEWARE_IMAGES`，避免测试机 Docker Hub 拉取超时）→ 收集 N4-monitor 代码 + `.env` → 解析各中间件 compose 的 bind-mount 源路径，**配置类目录完整复制、数据类目录（`DATA_DIRS`）只建空结构** → 打成单个 tar.gz。

### 8.3 测试机还原

```bash
# 步骤 0：传包（任选一种）
rsync -avP root@47.121.30.136:/opt/N4-monitor/n4-monitor-pack-<时间戳>.tar.gz /opt/
# 步骤 1：解压（unpack.sh 在包里）
cd /opt && sudo tar -xzf n4-monitor-pack-<时间戳>.tar.gz
# 步骤 2：给脚本加执行权限（git 检出可能丢执行位）
sudo chmod +x /opt/N4-monitor/deploy/unpack.sh /opt/N4-monitor/deploy/pack.sh
# 步骤 3：还原（从 deploy 目录运行，包用绝对路径）
cd /opt/N4-monitor/deploy
sudo ./unpack.sh /opt/n4-monitor-pack-<时间戳>.tar.gz
```

脚本动作：`docker load` 导入全部随包镜像 → 放代码到 `/opt/N4-monitor` → 放中间件 compose + 配置目录 + 空数据目录到 `/opt/<name>` → 逐个 `docker compose up -d` 启动中间件 → 启动 N4-monitor（镜像已加载则**不重建**，仅镜像缺失时 `docker compose build`）。

### 8.4 各中间件迁移策略（实测核实）

| 中间件 | 挂载路径 | 处理 | 说明 |
|---|---|---|---|
| emqx | `/opt/emqx/data`、`/opt/emqx/log`（绝对） | 空结构 | 运行时数据 + 日志；Dashboard 配置不迁移 |
| fuxa | `./appdata`（相对） | **完整复制** | FUXA 组态工程 + 用户，不可再生 |
| fuxa | `./db`、`./logs` | 空结构 | DAQ 历史 + 日志 |
| fuxa | `./images` | 完整复制 | 基本为空 |
| kafka | named volume `kafka_data` | 不处理 | 消息不迁移 |
| mysql | `./conf`（相对） | **完整复制** | MySQL 配置（utf8mb4 等） |
| mysql | `./data`、`./log` | 空结构 | 数据库文件；测试机空库用种子 SQL 初始化 |
| redis | `/opt/redis/conf/redis.conf`（绝对） | **完整复制** | Redis 配置 |
| redis | `/opt/redis/data` | 空结构 | RDB/AOF，空库启动 |
| tdengine | `/opt/tdengine/data`、`/log`（绝对） | 空结构 | 时序数据 + 日志 |

> 测试机 IP 不同时：还原后更新 N4-monitor 与各中间件 `.env` 里的 IP（同机统一 `127.0.0.1`，FUXA iframe 除外），再 `docker compose up -d`。
> 重复 `unpack.sh` 会覆盖 `/opt/N4-monitor` 与中间件 compose，但**不会清已存在数据卷**（up 时复用）；要彻底重置测试库先 `docker compose down -v`。

## 九、常用运维命令与排查

### 9.1 运维命令

```bash
docker compose ps                          # 状态
docker compose logs -f                     # 全部日志
docker compose logs -f n4-monitor-backend  # 仅后端
docker compose restart n4-monitor-backend  # 重启单个
docker exec -it n4-monitor-backend sh      # 进容器
docker stats                               # 资源占用
free -h                                    # 宿主机内存
ss -tlnp | grep -E ":80|:8088"             # 端口占用
```

### 9.2 常见问题

1. **后端连不上中间件**：host 模式下容器访问宿主机中间件用回环地址（`127.0.0.1`）。若中间件绑了 `0.0.0.0` 且有防火墙，需放行或改监听。容器内 `telnet 127.0.0.1 3306` 排查。
2. **前端空白 / 404**：`docker compose logs n4-monitor-frontend` 看 Nginx；确认 80 端口无冲突。
3. **FUXA iframe 不显示**：确认 FUXA 容器运行、浏览器能直连 `http://<IP>:1881`；改 `FUXA_BASE_URL` 后需 `docker compose build n4-monitor-frontend`（构建期注入）。
4. **TDengine 时间戳偏移**：确认容器 `TZ=Asia/Shanghai`、连接串 `jdbc:TAOS-RS://`（REST 模式免原生库时区依赖）。
5. **Kafka 消费者组冲突**：本地开发与服务器共用同一 group-id 会抢占消息。内嵌作业 group-id 默认 `n4-flink-alarm-processor`（application.yaml）；独立集群 `n4-flink-alarm-processor-prod`（compose）。部署前停本地后端或改 group-id。
6. **内存不足（OOM）**：后端 `-Xmx1024m` + Flink 内嵌开销，建议宿主机 ≥2GB 可用内存；不足时调 `JAVA_OPTS` 为 `-Xms256m -Xmx512m`。
7. **FUXA 舱视图超时**：舱视图就绪握手超时为 60s（`FuxaCabinMonitorPanel.vue`）。若 60s 仍提示 "did not become ready"，是 FUXA 端没正常响应握手（视图名配置或 bridge 脚本问题），不是超时长短问题。
8. **报警弹窗被遮挡**：全局报警 Toast 栈 z-index 已提至 9999，位于所有遮罩之上；若再被遮挡，检查是否有更高 z-index 的遮罩。

## 十、安全约定（.env 不入库）

- `.env` **不纳入版本控制**：`.gitignore` 忽略 `*.env`（仅放行 `.env.example`），git 历史已通过 filter-repo 重写清除，仓库中不存在 `.env` 内容。
- **请勿把 `.env` 加入 git 跟踪/推送**。口令一旦进入 git 历史，仅删除文件无法作废，必须到服务端逐一改密轮换；误提交时需 filter-repo 重写历史并轮换受影响口令。
- 每台部署机从 `.env.example` 创建本地 `.env` 并填写真实口令。
- 更多细节见仓库根 `README.md` 与 `.env.example` 顶部注释。
